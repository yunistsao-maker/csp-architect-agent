Architecture Overview

This diagram shows an end-to-end MLOps platform on AWS, laid out as five left-to-right stages inside a private VPC. Data is ingested, versioned and turned into features. SageMaker Pipelines then runs distributed training and evaluation, and the result goes to a Model Registry with a human approval gate. Approval triggers a CI/CD pipeline that deploys real-time and batch inference. Model Monitor watches the production data, and a drift or quality alarm automatically starts the training pipeline again (the pink dashed loop).

Security and observability (IAM, KMS, PrivateLink, Secrets Manager, CloudTrail, CloudWatch Logs, Config, Macie) apply across all stages and are shown in the bottom band.

Component Details

  • Kinesis Data Firehose / S3 Data Lake / Glue: Firehose ingests streaming data into the S3 lake, and Glue handles ETL and the Data Catalog.
  • S3 Versioned Datasets + CodeCommit (DVC): Immutable, versioned training datasets in S3. Git holds code and DVC pointer files, so every model can be traced to an exact dataset and code commit.
  • SageMaker Feature Store: Online store for low-latency inference features and offline store for training. The same feature definitions are used in both, which avoids training/serving skew.
  • SageMaker Pipelines: Orchestrates processing, training, evaluation and conditional registration as a DAG.
  • Distributed Training: Multi-node GPU training jobs using data or model parallelism, with managed Spot capacity and custom images from ECR.
  • Experiments (managed MLflow): Tracks parameters, metrics and artifacts for every run.
  • Studio: Notebooks and IDE for data scientists. Code is committed to CodeCommit.
  • Model Registry + Model Cards: Versioned model packages with metrics, lineage and status (PendingManualApproval, Approved or Rejected).
  • Approver, EventBridge, CodePipeline, CodeBuild, CloudFormation: An approved status change triggers CI/CD. The pipeline runs tests, deploys to staging, then to production through IaC.
  • API Gateway + Lambda + Real-time Endpoint: Clients call a private, WAF-protected API. Lambda pre- and post-processes and invokes an auto-scaling, multi-AZ endpoint.
  • Batch Transform + Step Functions + Scheduler: Scheduled or event-driven batch scoring, with input and output in S3.
  • Model Monitor: Compares captured traffic and ground-truth labels against baselines for data quality, drift, model quality and bias.
  • CloudWatch, SNS, EventBridge rule, Lambda: Violations raise alarms, send notifications and start the retraining pipeline.
  • Security and logging band: IAM roles, KMS keys, VPC endpoints, Secrets Manager, CloudTrail, CloudWatch Logs, Config and Macie.

SageMaker capabilities share the standard SageMaker icon and are distinguished by their labels, because draw.io has no separate icon for each one.

Data Flow

  1. Source systems stream or batch data through Firehose into the S3 data lake.
  2. Glue cleans and catalogs the data, writes versioned datasets to S3 and ingests features into Feature Store. DVC pointers are committed to Git.
  3. A data scientist works in Studio and commits pipeline code to CodeCommit.
  4. SageMaker Pipelines reads features and datasets, runs Processing, then distributed Training using the ECR image.
  5. Training and evaluation log to Experiments. Artifacts and metrics are written to S3.
  6. If the metrics pass the threshold, the model is registered in the Model Registry as PendingManualApproval.
  7. An approver reviews the model and sets it to Approved. EventBridge detects the state change and starts CodePipeline.
  8. CodeBuild runs tests, then CloudFormation deploys to staging and production, creating the real-time endpoint and the batch job definition.
  9. Clients call API Gateway, then Lambda, then the endpoint. Requests and predictions are captured to S3.
  10. Batch scoring runs on a schedule through Step Functions and Batch Transform.
  11. Model Monitor analyses captured data and ground-truth labels, writes reports to S3 and publishes metrics to CloudWatch.
  12. A CloudWatch alarm notifies through SNS and fires an EventBridge rule. Lambda then starts the SageMaker Pipeline, closing the loop.

Benefits

  • Full reproducibility: dataset version, code commit, features, hyperparameters and model are all linked.
  • Governed releases: a mandatory approval gate and an automated, tested deployment path.
  • Continuous quality: drift and performance degradation are detected and trigger retraining without manual work.
  • Scalable: managed distributed training, auto-scaled endpoints and serverless glue services.

Security Considerations

  • Run all SageMaker jobs and endpoints in private subnets with network isolation. Reach AWS services only through VPC endpoints (S3 gateway, SageMaker API and Runtime, ECR, Logs, STS).
  • Use separate least-privilege IAM roles for data engineering, training, pipeline execution, CI/CD and inference. Add permission boundaries and SCPs.
  • Encrypt S3, EBS volumes, Feature Store, model artifacts and endpoint storage with customer-managed KMS keys. Enforce TLS in transit.
  • Keep credentials in Secrets Manager. Use Macie to find PII before it enters training data.
  • Enable CloudTrail, CloudWatch Logs and Config rules for audit and compliance. Protect API Gateway with WAF and IAM or Cognito authorization.

Cost Optimization

  • Use Managed Spot Training with checkpointing for training jobs.
  • Use Savings Plans, multi-model endpoints and auto-scaling for real-time inference. Use Serverless Inference for spiky traffic.
  • Prefer Batch Transform for non-latency-sensitive workloads.
  • Use S3 lifecycle policies on raw data and captured traffic. Sample the data capture percentage.
  • Use Pipeline step caching to skip unchanged steps.

Best Practices

  • Define all infrastructure and pipelines as code, and use separate AWS accounts for dev, staging and prod.
  • Use champion/challenger or canary deployments with automatic rollback on alarms.
  • Create Model Monitor baselines from the training data, and set alarm thresholds carefully to avoid retraining storms.
  • Tag all resources and propagate lineage into Model Cards.
  • Keep the retraining trigger rate-limited, and gate the resulting model through the same registry approval.

Architecture Overview

This is an event-driven, pipeline-centric MLOps platform built on Vertex AI and the surrounding GCP data and DevOps services. Data flows from sources into a lake and warehouse, is versioned and served as features, and feeds reproducible, containerized training pipelines. Trained models pass through a registry and an approval gate, are deployed by CI/CD, and are served in real-time or batch mode. Monitoring closes the loop by triggering retraining automatically.

Security (IAM, CMEK, private networking, VPC Service Controls) and observability (logging, monitoring) apply across all stages.

Note: the icons use draw.io's mxgraph.gcp2.hexIcon with prIcon names. Vertex AI services share the generic ML icon because gcp2 has no per-service Vertex shapes, so the labels carry the service names. If an icon appears blank in your draw.io version, replace it from the Google Cloud shape library, and keep the labels.

Component Details

  • Pub/Sub and Dataflow: Streaming and batch ingestion and ETL into the lake and warehouse.
  • Cloud Storage and BigQuery: Raw and curated data lake plus analytical warehouse, used as offline feature and training sources.
  • Dataset Versioning: GCS object versioning, BigQuery snapshots and time travel, and Dataplex lineage. Immutable dataset version IDs are recorded with every run.
  • Vertex AI Feature Store: Offline features for training and low-latency online features for serving, which avoids training/serving skew.
  • Vertex AI Workbench, Experiments and ML Metadata: Interactive development, run, metric and parameter tracking (TensorBoard), and artifact lineage.
  • Vertex AI Pipelines: Orchestrates data validation, preprocessing, hyperparameter tuning (Vizier), distributed training (custom jobs on GPU/TPU), and evaluation.
  • Git Repo, Cloud Build and Artifact Registry: CI runs tests, builds training and serving images, and compiles pipeline specs. CD deploys approved models.
  • Vertex AI Model Registry and Approval Gate: Versioned models with metrics and lineage. Promotion requires passing automated thresholds plus a manual approval.
  • Online Endpoint and Batch Prediction: Autoscaled private real-time serving and scheduled large-scale scoring written to BigQuery or GCS.
  • Model Monitoring, Cloud Monitoring, Pub/Sub and Cloud Functions: Detect drift, skew and performance decay (using ground-truth labels), alert, and submit a new pipeline run.
  • Security and Observability layer: IAM, KMS, VPC/PSC, VPC Service Controls, Cloud Logging and Audit Logs, and Cloud Monitoring.

Data Flow

  1. Sources publish to Pub/Sub or batch-load. Dataflow cleans the data and writes to Cloud Storage and BigQuery, creating versioned snapshots.
  2. BigQuery populates the Feature Store (offline and online).
  3. A Git commit triggers Cloud Build. It tests the code, builds images into Artifact Registry, and compiles and submits the Vertex AI Pipeline.
  4. The pipeline pulls a dataset version and features, validates the data, preprocesses it, tunes hyperparameters, and runs distributed training. It logs to Experiments and ML Metadata.
  5. The pipeline evaluates the model and registers it in the Model Registry.
  6. The approval gate checks metrics and requires a manual sign-off. Cloud Build CD then deploys the model.
  7. Deployment goes to the online endpoint (canary or traffic split) and to batch prediction jobs.
  8. Clients call the endpoint, which fetches online features. Request and response logs flow to Model Monitoring.
  9. Model Monitoring compares serving data with the training baseline and with ground truth. A threshold breach raises a Cloud Monitoring alert, publishes to Pub/Sub, and a Cloud Function re-submits the pipeline.

Architecture Patterns / Database Design Patterns

  • Event-driven automation: Pub/Sub and Eventarc connect alerts to retraining.
  • Pipeline-as-code (CI/CD/CT): Continuous integration, delivery and training from Git-defined pipelines.
  • Feature Store pattern: One feature definition for training and serving.
  • Gated promotion: A model registry with a policy and manual approval gate.
  • Defense in depth: Private connectivity, a service perimeter, CMEK, and least-privilege identities.

Benefits

  • Reproducibility through data version, code version, container image and metadata lineage.
  • Automated, closed-loop retraining on drift or performance decay.
  • Consistent features between training and serving.
  • Governed releases with an auditable approval trail.
  • Managed, autoscaling infrastructure with lower operational burden.

Design Considerations

  • Separate dev, staging and prod projects. Promote the same model artifact across them.
  • Choose drift thresholds and retraining cadence carefully to avoid retraining storms and cost spikes.
  • Ground-truth labels often arrive late, so use proxy metrics in the meantime.
  • Use Reduction Server, Spot VMs and TPU/GPU quotas for cost-effective distributed training.
  • Private endpoints require Private Service Connect or VPC peering plus DNS planning.

Best Practices

  • Use a dedicated service account per component (pipeline, training, serving, CI/CD) and Workload Identity.
  • Enable CMEK on all data and model storage, and route Audit Logs to a log sink or BigQuery.
  • Keep an offline evaluation and a shadow or canary deployment step before 100% traffic.
  • Pin container image digests and register the dataset version with each model.
  • Alert on pipeline failures, endpoint latency and error rates, and cost budgets, not just model drift.

Architecture Overview

This is an end-to-end MLOps platform on Azure, organized as six horizontal tiers. Data flows from ingestion and feature engineering, through versioned training and tracking in Azure Machine Learning, and into a gated model registry. Azure DevOps handles CI/CD, and the model is served through real-time (AKS) and batch (AML Batch Endpoint) inference.

A closed loop sits on top of this. Azure Monitor and AML Model Monitoring detect data drift and performance decay, publish events to Event Grid, and an Azure Function triggers a retraining pipeline. Security (Entra ID, Key Vault, private networking) and centralized logging span every tier.

Component Details

  • Data Factory / Event Hubs: Batch and streaming ingestion from SQL, SaaS, files and IoT sources.
  • ADLS Gen2 + Delta Lake: Lakehouse storage (bronze/silver/gold). Delta time travel gives data versioning.
  • Azure Databricks: Scalable Spark transformations and feature engineering.
  • AML Managed Feature Store: Offline store for point-in-time training sets. It is materialized to Redis as the online store for low-latency inference.
  • Versioned Data Assets: Immutable, versioned dataset references in the AML workspace that tie each model to its exact data.
  • AML Pipeline + GPU Cluster: Reproducible prep → train → evaluate pipeline. Distributed training runs on a GPU cluster (PyTorch DDP/Horovod).
  • Experiment Tracking (MLflow): Parameters, metrics, artifacts and run comparison.
  • Model Registry + Approval Gate: Versioned models with lineage. Promotion requires metric thresholds plus a manual approval.
  • Azure DevOps: CI/CD that builds the scoring image, runs tests and deploys. It also receives retrain triggers.
  • Container Registry: Stores versioned scoring images.
  • Staging tests: Smoke, load and shadow tests before production promotion.
  • AKS + API Management: Real-time scoring with blue/green rollout and autoscaling, fronted by authentication and throttling.
  • AML Batch Endpoint: Scheduled large-scale scoring that writes predictions to ADLS.
  • Azure Monitor / App Insights / AML Model Monitoring: Operational telemetry plus data drift, prediction drift and performance monitoring.
  • Event Grid + Azure Function: Event routing and the automated retraining trigger.
  • Log Analytics, Key Vault, Entra ID, VNet, Private Link: Central logging, customer-managed keys and secrets, RBAC and managed identities, network isolation and private endpoints.

Data Flow

  1. Batch data (Data Factory) and streaming data (Event Hubs) land in ADLS Gen2 Delta tables.
  2. Databricks cleans the data and builds features, which are published to the Feature Store. Features are materialized to the Redis online store.
  3. A point-in-time training set is registered as a versioned data asset.
  4. The AML pipeline runs distributed training on the GPU cluster and logs runs to MLflow.
  5. The best model is registered, then passes the approval gate (automatic metric checks plus manual sign-off).
  6. Azure DevOps builds the image, pushes it to ACR and deploys it to staging for tests.
  7. After tests pass, the model is promoted to AKS (real-time, behind API Management) and the Batch Endpoint.
  8. Telemetry and captured inference data go to Azure Monitor/App Insights and AML Model Monitoring. Diagnostics are sent to Log Analytics.
  9. A drift or performance breach raises an Event Grid event. The Azure Function starts the DevOps pipeline, which submits a retraining job, and the loop repeats.

Architecture Patterns / Database Design Patterns

  • Lakehouse (medallion): Bronze/silver/gold Delta layers give lineage and reproducibility.
  • Feature Store (offline/online): Consistent features for training and serving, avoiding training/serving skew.
  • Event-driven retraining: Monitor → Event Grid → Function → pipeline.
  • Gated promotion / GitOps-style CD: Registry approval plus staging validation before production.
  • Blue/green deployment: Safe rollout and rollback on AKS.
  • Zero-trust networking: Private endpoints with managed identities and no public access.

Benefits

  • Full reproducibility through data, code, model and environment versioning.
  • Automated, governed path from experiment to production.
  • Continuous quality assurance via drift detection and automated retraining.
  • Secure, auditable and compliant by design.

Design Considerations

  • Set drift and performance thresholds, with cooldowns to prevent retrain storms.
  • Choose AKS or AML managed online endpoints depending on how much cluster control you need.
  • Plan GPU quotas and low-priority/spot nodes for cost control.
  • Ground-truth labels often arrive late, so performance monitoring needs a label-join job.
  • Use private DNS zones for all Private Link endpoints.

Best Practices

  • Use managed identities instead of keys, and store secrets and CMKs in Key Vault.
  • Separate dev/test/prod workspaces and subscriptions, and define infrastructure as code (Bicep/Terraform).
  • Pin environments and container images, and sign and scan images in ACR.
  • Enforce Azure Policy and diagnostic settings so all logs reach Log Analytics.
  • Always retrain through the same pipeline and approval gate used for new models.
